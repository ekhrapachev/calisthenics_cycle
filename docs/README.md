но не заменяют правила поведения.

## Структура

```text
docs/
├── README.md                  # эта навигация
├── product-overview.md        # назначение продукта и baseline
├── main-user-flow.md          # основной путь пользователя
├── specs/                     # требования и подробные сценарии
├── engineering/               # архитектура, API и модель данных
├── prototypes/                # актуальный и ранний HTML-прототипы
├── mockups/
│   ├── current/               # принятые макеты текущей версии
│   └── concepts/              # варианты и продуктовые исследования
└── research/                  # методика тренировок и контентные источники
```

## Статусы материалов

- **Актуально:** `product-overview.md`, `main-user-flow.md`,
  `specs/business-requirements.md`, `specs/user-scenarios.md`,
  `prototypes/current.html` и `mockups/current/`.
- **Концепт:** `mockups/concepts/`. Эти материалы полезны для истории решений,
  но сами по себе не являются утверждённым интерфейсом.
- **Архив:** `prototypes/legacy-push-pull.html` и
  `specs/workout-routines-handoff.md`.
- **Исследование:** `research/`. Это источник для продуктовых решений, а не
  обещание текущего поведения приложения.

## Правило следующей итерации

1. Обновить требование и затронутые сценарии.
2. Обновить основной сквозной сценарий, если меняется ключевой путь.
3. Обновить прототип или добавить макет изменяемого экрана.
4. Реализовать и проверить изменение.
5. После публикации обновить baseline в `product-overview.md`.
