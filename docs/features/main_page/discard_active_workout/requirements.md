# Функциональные требования

Фича: `discard_active_workout`

## Термины

- **Активная тренировка** — начатая и ещё не завершённая тренировка.
- **Отказ от тренировки** — удаление активной тренировки без пользовательской
  записи в истории и без влияния на статистику.
- **Отложенный старт** — намерение начать конкретную новую тренировку после
  отказа от текущей.
- **Состав активной тренировки** — неизменяемый массив `active.exercises` из
  `workout_session_snapshots.exercises_json`.
- **Точка продолжения** — `active.resume`, первая пара упражнения и подхода без
  сохранённого результата.

## Бизнес-правила

1. Одновременно у пользователя может быть не более одной активной тренировки.
2. Отказ возможен только для активной тренировки текущего пользователя.
3. Отказ не создаёт завершённую тренировку и не обновляет:
   - число тренировок;
   - объём, длительность, рекорды и серии;
   - прогресс плана;
   - историю выполненных упражнений.
4. Настройки, шаблоны и план тренировок пользователя не удаляются.
5. При отказе удаляется принадлежащая пользователю активная запись
   `workout_sessions`. Существующие внешние ключи с `ON DELETE CASCADE` удаляют
   её `workout_session_snapshots` и `workout_sets`.
6. Записи со статусом `completed` не удаляются.
7. Операция должна быть идемпотентной: повтор одного запроса не создаёт ошибочных
   записей и не меняет статистику.
8. Новая тренировка может начаться только после подтверждённого отказа от
   текущей.
9. Название, порядок, параметры и состав активной тренировки читаются из
   snapshot, а не из редактируемого `workout_routines`.
10. Просмотр состава не изменяет данные и не позволяет менять порядок или
    переходить к произвольному упражнению.
11. Продолжение с главной и из sheet использует один и тот же `active.resume`.
12. Упражнение считается выполненным, если все его пары `exerciseKey +
    setNumber` присутствуют среди `workout_sets`.

## Состояния интерфейса

| Состояние | Поведение |
|---|---|
| Нет активной тренировки | Показать обычный CTA старта |
| Есть активная тренировка | Показать карточку с названием, `resume`, составом, `Продолжить` и `Завершить` |
| Состав открывается | Показать skeleton строк, не менять активную тренировку |
| Состав открыт | Показать snapshot и выделить текущую строку |
| Ошибка состава | Сохранить компактную карточку и дать повторить загрузку |
| Открыто подтверждение | Фон недоступен для взаимодействия |
| Завершение выполняется | Заблокировать действия, показать progress state |
| Завершение успешно | Удалить активную карточку или продолжить отложенный старт |
| Завершение неуспешно | Сохранить карточку и прогресс, показать ошибку |

## Требования клиента

- Перед destructive-операцией всегда показывать подтверждение.
- Рендерить карточку из уже загруженного объекта `active` ответа
  `GET /api/workouts`; отдельный API-запрос для состава не требуется.
- Не копировать snapshot в новое состояние: `activeExercises` остаётся единым
  источником списка.
- Вычислять состояния строк относительно `activeResume.exerciseIndex`.
- Для текущей строки показывать `activeResume.setNumber`; предыдущие упражнения
  считать выполненными, следующие — предстоящими.
- Оба CTA продолжения вызывают существующий `resumeWorkout()`.
- Не оптимистично удалять карточку до подтверждённого успеха.
- Заблокировать повторное нажатие на время операции.
- После успеха инвалидировать/обновить активную тренировку, главную страницу,
  историю и статистику.
- При отложенном старте хранить намерение только до успеха, отмены или ухода со
  страницы.
- Если приложение закрылось во время операции, после запуска получить
  фактическое состояние из источника истины.
- Если тренировка уже завершена на другом устройстве, синхронизировать состояние
  и считать пользовательский результат успешным.

## Серверный контракт Forma

```http
POST /api/workouts/{workoutId}/discard
```

Успешный ответ:

```json
{
  "ok": true,
  "workoutId": "uuid"
}
```

Endpoint:

- требует cookie-сессию `forma_session`;
- удаляет только строку с совпадающими `id`, `user_id` и `status = 'active'`;
- не вызывает `/complete` и не создаёт строку истории;
- возвращает тот же успешный ответ при повторе, чтобы запрос был идемпотентным;
- не сообщает, существует ли чужой, завершённый или уже удалённый ID.

Ожидаемая обработка:

- `200` — успешно или тренировка уже не активна;
- `401/403` — не менять локальное состояние, применить текущий auth-flow;
- `5xx/offline` — сохранить прогресс и дать повторить.

Изменение схемы D1 не требуется: каскадное удаление уже описано в
`docs/engineering/data-model.md`, а история `GET /api/workouts` выбирает только
сессии со статусом `completed`.

## Нефункциональные требования

- Время визуального отклика на нажатие — до 100 мс.
- Целевое завершение операции при нормальной сети — до 2 секунд.
- Все тексты локализуемы и не собираются конкатенацией.
- Логи не содержат введённые пользователем заметки и медицинские/чувствительные
  данные.
- После перезапуска `GET /api/workouts` возвращает фактическое состояние D1.

## Acceptance criteria

```gherkin
Feature: Активная тренировка на главной

  Scenario: Пользователь видит точку продолжения
    Given есть активная тренировка с resume для упражнения 2, подхода 3
    When пользователь открывает главную
    Then карточка показывает название snapshot
    And показывает название упражнения 2
    And показывает "подход 3" и общее число подходов упражнения

  Scenario: Пользователь просматривает состав
    Given есть активная тренировка с выполненными и предстоящими упражнениями
    When пользователь нажимает карточку активной тренировки
    Then упражнения показаны в порядке snapshot
    And завершённые упражнения отмечены как выполненные
    And упражнение из resume отмечено "Продолжим отсюда"
    And будущие упражнения не являются ссылками

  Scenario: Продолжение из состава
    Given открыт состав активной тренировки
    When пользователь выбирает "Продолжить"
    Then открывается упражнение и подход из active.resume
    And новая workout_session не создаётся

  Scenario: Пользователь подтверждает отказ
    Given у пользователя есть активная тренировка с прогрессом
    When он выбирает "Завершить"
    And подтверждает "Завершить без сохранения"
    Then активной тренировки больше нет
    And тренировка не появляется в истории
    And статистика и прогресс плана не меняются
    And пользователь может начать новую тренировку

  Scenario: Пользователь отменяет отказ
    Given открыто подтверждение завершения
    When пользователь выбирает "Продолжить тренировку"
    Then подтверждение закрывается
    And активная тренировка и её прогресс сохраняются

  Scenario: Пользователь начинает новую тренировку
    Given у пользователя есть активная тренировка
    When он выбирает новую тренировку
    And подтверждает завершение текущей без сохранения
    Then текущая тренировка удаляется без влияния на статистику
    And система продолжает старт выбранной новой тренировки

  Scenario: Операция завершается ошибкой
    Given у пользователя есть активная тренировка
    When запрос завершения возвращает ошибку
    Then активная тренировка и прогресс остаются доступными
    And пользователь видит ошибку
    And может повторить действие
```
