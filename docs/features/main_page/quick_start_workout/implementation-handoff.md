# Handoff для реализации

## 1. Затрагиваемые поверхности

Основная текущая реализация:

- `app/FormaApp.tsx`;
- `app/globals.css`;
- `app/api/workouts/route.ts`;
- при необходимости новый endpoint чтения позиции активной сессии;
- общие требования в `docs/product/`.

Изменение схемы БД не обязательно: позицию можно вычислить по
`workout_session_snapshots` и `workout_sets`. Если вводится отдельная позиция,
она должна оставаться производной или обновляться атомарно с сохранением
подхода.

## 2. Изменения клиентского состояния

Главная должна принимать единое состояние загрузки:

```ts
type HomeWorkoutState =
  | { status: "loading" }
  | { status: "ready"; active: null; routines: Routine[] }
  | {
      status: "ready";
      active: {
        id: string;
        routineName: string;
        exercises: Exercise[];
        resume: { exerciseIndex: number; setNumber: number };
      };
      routines: Routine[];
    }
  | { status: "error"; message: string };
```

Не вычислять режим CTA до завершения загрузки и активной сессии, и наборов.

Добавить UI-состояния:

- `workoutPickerOpen`;
- `startingRoutineId`;
- `resumingWorkout`;
- локальная ошибка выбора/запуска.

## 3. Рендер главной

Удалить из `home`:

- `.home-routines`;
- `.routines-heading`;
- compact-список наборов;
- `.new-routine-button`.

Добавить для `screen === "home"` существующий паттерн `.screen-action`.

Условие:

```text
active != null → активное имя + «Продолжить тренировку»
active == null → «Начать тренировку»
```

Экран `routines` и его закреплённая кнопка создания остаются.

## 4. Запуск

Текущая функция запуска зависит от `selectedRoutine`. Для нового сценария она
должна принимать явный идентификатор:

```ts
startWorkout(routineId: string)
```

Карточка в панели вызывает `startWorkout(routine.id)`.

Во время запроса:

- заблокировать повторный запуск;
- сохранить панель в текущем контексте;
- после успеха записать данные снимка и перейти к упражнению;
- после ошибки разблокировать карточки и показать сообщение.

## 5. Продолжение

Не использовать создание тренировки как единственный механизм продолжения.
Текущий POST отклоняет запрос без `routineId` до поиска активной сессии. Это
ломает продолжение с главной и продолжение после удаления исходного набора.

Допустимые варианты контракта:

### Рекомендуемый

`GET /api/workouts` возвращает активную сессию вместе с `resume`:

```json
{
  "active": {
    "id": "workout-id",
    "routineName": "Push day",
    "exercises": [],
    "resume": {
      "exerciseIndex": 1,
      "setNumber": 2
    }
  }
}
```

Клиент продолжает уже загруженную активную сессию без POST.

### Допустимый

Отдельный идемпотентный endpoint:

```text
GET /api/workouts/active
```

Он возвращает снимок и позицию или `null`.

Не рекомендуется требовать `routineId` для чтения активной сессии.

## 6. Вычисление `resume`

API загружает все сохранённые пары `exercise_key + set_number` активной сессии.
Затем обходит упражнения снимка и ищет первую отсутствующую пару.

Важно:

- использовать упражнения снимка, а не каталога исходного набора;
- не полагаться на существование `routine_id`;
- учитывать legacy-снимки;
- если все подходы сохранены, не возвращать `{0, 1}`.

## 7. Серверная защита от дублей

Текущая предварительная проверка активной сессии полезна, но сама по себе не
гарантирует защиту при двух параллельных запросах.

Реализация должна обеспечить MP-11 одним из способов, совместимых с D1:

- транзакционная/атомарная операция;
- уникальное серверное ограничение для активной сессии пользователя;
- сериализованный idempotency key на клиентскую попытку запуска.

Выбранный механизм покрыть тестом конкурентного запуска.

## 8. Навигация

Нужно различать точку входа в выполнение:

```ts
type WorkoutEntry = "home" | "routine";
```

- запуск/продолжение с главной → назад на главную;
- запуск из деталей → назад в детали;
- возврат не очищает активную сессию.

## 9. Проверки

Минимальный набор:

1. Главная без активной сессии.
2. Открытие и закрытие выбора.
3. Запуск каждого доступного набора.
4. Главная с активной сессией.
5. Продолжение после обычного возврата.
6. Продолжение после перезагрузки.
7. Продолжение после удаления исходного набора.
8. Пустой список наборов.
9. Ошибка загрузки.
10. Ошибка и повтор запуска.
11. Двойное нажатие.
12. Параллельный запуск в двух вкладках.
13. Все подходы сохранены, но завершение сессии не было подтверждено.
14. Keyboard/focus-поведение панели.
15. Мобильная safe area и отсутствие перекрытия контента.

После реализации выполнить существующие:

- typecheck;
- lint;
- production build;
- ручной проход основного сценария.
